# 项目总结

做这个 IEC 61499 分布式工业控制系统项目，是我对工业控制软件架构演变方向的一次系统性实践。之前做"边缘网关"项目时，我解决的是"设备协议怎么接入、数据怎么上报云端"的问题——那是一个南北向数据管道；而这个项目要回答的问题明显更深一层：当控制逻辑本身分布到多个节点之后，系统应该以什么样的模型来组织、调度和容错。可以说边缘网关让我理解了数据流的分布式，这个项目则让我动手实现了控制流的分布式。

选 IEC 61499 作为建模标准，源于我对行业趋势的判断：传统 PLC 的周期扫描模型在集中式控制里非常成熟，但智能产线把感知、决策、执行下沉到边缘设备后，"单控制器扫描一切"的模式在扩展性上遇到了天花板。IEC 61499 用事件驱动语义替代扫描语义，用功能块网络描述跨设备的应用，恰好是面向这种形态的标准。为了把对比做实，我特意让 PLC 节点里的传送带、气缸、伺服用事件驱动方式重新实现：传送带位置采用"事件到来时按物理方程惰性求值"，而不是每周期刷新。跑起来之后效果很直观——五个节点全部空闲时 CPU 占用接近于零，事件一到即刻执行，这是扫描模型做不到的。

事件驱动架构的核心难点不在"发事件"，而在事件洪峰下的秩序。我的方案是四级消息优先级加优先级队列：故障切换消息永远排在普通任务之前，哪怕任务再拥堵，心跳和切换通路也不会被淹没；同时用队列上限加"丢低保高"的背压策略防止雪崩。节点内部我没有搞两套调用语义，功能块之间的互连和跨节点通信一样走事件总线，只是消息 scope 标记为 local 不出网——这换来一个很重要的性质：应用拓扑的重构只改绑定配置，不改代码，这正是 IEC 61499"组态优于编程"理念的落地。

分布式一致性是这个项目里我思考最多的部分。热备要接管主控，最大的敌人是脑裂：备用节点切换的瞬间，原主控可能只是暂时卡顿而非真死。我没有引入 Raft 这类多数派共识，因为五十毫秒的切换时限容不下选举轮次，而系统的写者实际上只有一个（调度权）。最终采用"领导者租约 + epoch 围栏令牌"的组合：主控持续续约带 TTL 的租约，热备在心跳超时后强制接管并把纪元加一；所有任务派发消息携带纪元，工作节点拒绝旧纪元的指令，原主控恢复后读到租约已易主便自动让位并暂停派发。配合消息 msg_id 幂等去重（双通道并发收发的前提）和带纪元过滤的全量状态快照复制，整套方案在"单写者"前提下达到了等效唯一性保证。这是有意识的工程折中，我在设计文档里明确写了它的适用边界。

热备的五十毫秒指标，靠的不是切换时做得快，而是把重活全部前置：队列快照常驻热备内存、路由连接预建、租约文件就在本地。切换动作只剩三次内存操作、一次小文件原子写和一条 CRITICAL 事件发布，实测一点四二毫秒完成，恢复三十一个排队任务。真正的恢复延迟瓶颈是一点五秒的失联检测窗口——这是误判率和检测速度之间的折中，可按产线容忍度配置。用故障注入器做混沌验证时，宕机、延迟、丢包三类故障都能被这套机制吸收，这个结果让我对设计方案有了实测层面的信心，而不只是纸面推演。

回望两个项目的递进关系：边缘网关让我掌握了协议适配、断线缓存、数据上云这些"连接层"的工程能力；这个项目则把战场推进到"控制层"——我需要自己定义消息信封、设计优先级调度、处理分布式失败场景、实现租约与围栏、还要让这一切可观测（Web 控制台的拓扑、事件流、在线组态都是为此服务的）。如果说前者教会我怎么把设备接入网络，后者让我理解的是：把控制逻辑本身分布出去之后，一致性、容错和可观测性会变成系统设计的第一等问题，而事件驱动是贯穿这三者的统一抽象。这段实践让我对"从集中到分布"的行业演进有了手感级的理解，也让我明确了自己在工业软件方向上继续深挖的路径。
